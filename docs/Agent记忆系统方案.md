# Agent 记忆系统开发方案（v2）

更新：2026-09-27。v1 已按下方开发顺序实现、完成验收并部署到服务器；本轮未提交或推送 Git，等待用户统一确认。

## 已确认的产品规则

- 首版长期偏好只在用户**明确要求记住**时写入。自动提取先留在后续计划，未来可结合用户要求与“自动提取后确认”，不在首版静默保存。
- 删除会话只删除该会话及消息；已保存的长期偏好单独查看、修改和删除。
- Android 首版提供完整对话列表、新建对话、打开历史对话和删除对话。
- 按登录账号隔离。当前同一账号在多台设备上看到同一份会话和偏好，与现有旅行记录的归属一致；不另建设备级身份。

## 现状与目标

每次 Android 只向 `POST /api/v1/agent/chat` 发送当前一句话；服务端每次新建 `TravelAgentState`，LangGraph 虽有 `messages` 字段，却没有跨请求的会话 ID 或持久化。Android 消息列表也只保存在当前 ViewModel。因此“南京有什么景点？”之后问“美食呢？”无法稳定继承南京，退出页面后聊天内容还会消失。

目标分成两类：

- **短期会话记忆**：同一个对话内理解“那里、第二天、那美食呢”等指代，并在重新打开 App 后展示该对话。不同对话不自动混用上下文。
- **长期偏好记忆**：跨对话记住用户明确指定的旅行偏好，例如“不吃辣、喜欢博物馆、行程别太赶”。已去过的城市、景点、美食继续以现有 Trip/Record 为准，不能从模型记忆推断或复制一份可能过时的清单。

## 推荐的第一版

### 1. 会话与短期上下文

在服务端 SQLite 增加 `chat_conversations` 与 `chat_messages`，都绑定 `user_id`。聊天请求增加可选 `conversation_id` 和用于重试去重的 `client_message_id`；响应返回 `conversation_id`。旧客户端只传 `message` 仍可正常问答，但不获得跨请求上下文。新建对话时由服务端生成 ID，后续消息带同一个 ID。Android 展示按最近活动排序的完整对话列表，支持新建、打开、删除；列表和消息可分页，不设置自动过期。现有 App 内存中的旧消息没有服务端副本，无法补录，从新版本开始保存。

短期记忆采用三层，而非只取最近 8 轮：

1. **完整原文**：`chat_messages` 按会话永久保存用户和助手消息，供列表展示、追溯与原文回查；压缩不修改或删除原文。
2. **当前会话状态**：按会话保存当前话题（例如“规划南京三日游”）、正在讨论的子问题或日期、已确认的目的地、日期/天数、人数、预算、饮食与景点限制等本次任务条件，并记录来源消息 ID。追问先结合话题、状态与近期原话解析指代，再交给需求分析；不能简单拼接旧提问和新消息。用户明确切换话题或更正条件时更新状态；切换后想回到旧话题，可从摘要与原文回查；多个话题均可能匹配时先澄清。未确认的推荐、过期的天气与 POI 结果不写入状态。状态只属于当前会话，不自动成为长期偏好。
3. **近期上下文**：把最近若干完整问答、当前用户消息、当前会话状态和必要的旧对话摘要提供给需求分析。最近 **8 轮问答**只是初始上限，还须受 token 预算限制，不能保证每次都放入 8 轮；裁剪只影响本轮模型输入，不影响完整原文。

后续仍使用本轮独立的 `TravelRequirement`、信息状态和工具结果。不把上一轮的 POI、天气、预算估算、ToolMessage 或整个 LangGraph State 自动复用为本轮事实，因为这些事实可能过期。历史记录每次从 Trip/Record 读取；天气、地点与费用按本轮需要重新查询或估算。新会话不继承旧会话的状态与摘要，但仍可使用显式保存的长期偏好。

### 2. 长会话压缩与原文回查

为每种 LLM 调用明确输入 token 预算，给系统提示、工具参数/结果和输出预留空间。会话记忆只占分配给它的预算，不直接占用模型最大上下文的 60% 或 75%。**初始触发阈值为会话记忆预算的 70%**；上线后依据实际 token 使用量、耗时和模型限制调整。每次调用前还要做硬上限检查，单条过长消息也不能突破预算。阈值统计的是尚未摘要的历史与近期消息，而不只是已经裁成 8 轮的输入，否则永远不会触发压缩。

达到阈值时，保留近期完整问答，将更早的未摘要消息按连续区间生成短摘要；摘要记录 `conversation_id`、起止 `message_id`、版本与更新时间。旧摘要和会话状态的长度同样设上限：长会话继续增长时，不把所有区间摘要无界拼接到提示词，而是仅放入当前相关的短摘要，其他摘要作为检索索引。摘要只帮助理解话题，不能覆盖已确认的结构化状态或原始消息；摘要生成失败时仍可使用状态与近期消息，并记录失败，不阻断正常问答。压缩应分块处理，避免一次把过长原文送入摘要模型；可在一轮完成后处理待摘要区间，下一轮调用前仍要检查预算。

当用户提到已超出近期窗口的具体内容，例如“按我前面说的那家店调整”，且状态或摘要不足以确定指代时，Agent 可回查同一会话的 SQLite 原文。工具至少支持按 `message_id` 区间读取，并可按关键词查找候选消息；返回带 ID 的少量原文片段，限制条数与 token 量。工具在需求分析/指代消解**之前**可用，避免错误意图已定后才发现需要回查。所有查询由服务端锁定当前 `user_id` 和 `conversation_id`，模型不能传入任意用户 ID；删掉会话后摘要、状态和回查索引一并删除。找不到或存在多个可能指代时询问用户，不把摘要的猜测当成原话。摘要和指针提高找回能力，但不能保证模型自动识别每一条遗漏的信息。

### 3. 工具调用索引与结果回查

每次实际调用工具后，在 SQLite 按会话保存一条调用记录：`tool_run_id`、触发消息 ID、工具名、**执行时的规范化参数**、调用时间、完成/失败状态、简短结构化概述，以及完整结果的引用。概述只提取结果中已有、便于检索的字段，如查询城市、日期、POI 名称、返回条数或失败原因；不能让模型凭空生成未返回的事实。完整的规范化结果单独落盘并关联 `tool_run_id`，压缩会话时不删除。引用是受服务端校验的 ID，不是给模型任意文件路径或 SQL 权限；工具密钥不进入调用记录。

每轮先按当前话题、工具名、规范化参数、时间和状态筛选相关调用；可把每种工具最近最多 2 条**相关概述与引用**作为初始候选，不机械注入最近 2 份完整结果，也不因相同工具名就认为不同城市/日期的结果可复用。只有当概述不足以回答“刚才为什么这样推荐”之类的追溯问题时，Agent 才通过受限工具按 `tool_run_id` 读取少量完整结果；回查能力在需求分析/指代消解之前可用，返回内容仍受条数和 token 预算约束。旧结果用于说明当时依据，不自动当成当前事实：天气、POI、费用等按本轮需求重新查询或估算，旅行记录以当前 Trip/Record 为准。删除会话时同时删除其工具调用记录与结果；长期偏好继续独立管理。

失败请求不写入“已完成回答”；网络重试带同一个 `client_message_id` 时返回已有结果或明确的处理中状态，避免重复计费与重复消息。Android 切换会话后，旧会话迟到的响应不能追加到当前会话。会话查询、发送和删除都按 `user_id` 限定；删除后原 ID 不可继续发送。

### 4. 长期偏好

增加独立的 `user_preferences` 表，首版只支持有限的结构化类别，如饮食忌口、景点兴趣、旅行节奏、预算倾向。仅当用户明确说“记住我不吃辣”或在个人中心主动填写时写入；“朋友不吃辣”“这次不吃辣”不应自动变成永久偏好。写入前核对类别、内容长度和主体；成功保存后才回复“已记住”。每条保存来源、修改时间，可在个人中心查看、更正、删除；同类新偏好覆盖旧值。用户明确说“忘记我不吃辣”时删除对应偏好。删除原对话不连带删除已保存的偏好。

需求分析先读取明确偏好，再和本轮要求合并；**本轮明确要求优先**。例如长期“喜欢慢节奏”，本轮“这次一天多看几个景点”按本轮执行。偏好只能影响推荐排序或约束，不能变成地点、开放时间、门票或用户旅行史等外部事实。

### 5. 为什么先不用向量库或完整 Graph checkpoint

当前单人小应用使用 SQLite 即可按会话 ID、用户 ID、消息 ID、工具调用 ID 和偏好类别查到所需数据；没有大量非结构化资料要做语义搜索。现有 Graph 的状态还包含本轮临时 POI、天气及校验结果，整包恢复容易把旧事实当成新事实。仅分别持久化原文、当前会话状态、有限摘要、工具调用记录与结果、明确偏好；暂不引入向量库或完整 Graph checkpoint。

## 开发顺序与验收

1. **数据与 API**：增加 Alembic 迁移、会话/消息表、可选 `conversation_id`、消息重试去重，以及会话列表/消息/删除接口。测试跨用户隔离、重复请求、旧客户端兼容、删除后不可读取；每一步跑服务端回归。
2. **三层短期记忆**：持久化当前话题与会话状态；需求分析先解析追问指代，再接收状态与受 token 预算约束的近期问答；Android 完成完整对话列表、新建、打开、删除和重启后恢复。测试“推荐南京景点 → 美食呢？”继承南京；超过 8 轮仍记得明确的预算和排除条件，更正会覆盖旧条件；换话题后回查旧话题，歧义时要求澄清；新会话不能继承；“明天呢？”天气须重新查明天，不能复用今天结果；切换对话后的迟到响应不能串到别的对话。
3. **压缩与回查**：增加区间摘要、来源消息 ID 与受限的原文查询；在预算的 70% 阈值附近触发分块压缩。增加工具调用索引、结构化概述、完整结果存储和受限回查。测试超长会话不超过输入预算、摘要不会覆盖更正、回查能找到早期原话和指定工具结果、不同城市/日期的工具调用不误用、旧天气须重新查询、跨用户及删会话后不能回查、摘要失败不阻断问答；观察摘要调用造成的延迟与费用。
4. **长期偏好**：迁移偏好表，提供显式写入、修改、读取、删除及个人中心管理。测试“记住我不吃辣”跨会话生效、“这次想吃辣”只覆盖本轮、“我朋友不吃辣”不写入，以及删除聊天不删除已保存偏好。
5. **回归与部署**：检查请求耗时和 LLM 上下文长度；跑历史、推荐、天气、距离、预算、规划及 401/超时回归。迁移前备份 SQLite；部署后真机检查对话切换、多设备同步和重启后恢复。

## 后续阶段：自动提取候选

首版稳定后，可增加从多轮对话中**自动提出**旅行偏好候选的功能，但仍需用户确认才能保存；与用户主动说“记住……”的入口并存。再根据实际聊天量与回查效果判断是否需要语义检索，不在首版引入向量数据库或自动写入。

**数据保护与边界：**原始对话不会因压缩而修改或删除；摘要和检索只改善找回机会，不保证模型自动发现每条旧信息。记忆、原文和工具结果查询都由服务端限制在当前用户与会话。完整工具结果仅在用户提出明确回查请求时加入上下文；旧天气、地点、价格不作为当前事实复用。token 数为保守估算，不是提供商 tokenizer 的精确计数；摘要每次最多处理两个分块，超长积压会在后续请求继续处理。真实模型长会话成本/延迟仍需后续线上观察。

**本轮未做：**偏好自动提取候选、向量检索、自动过期、旧历史迁移，以及 Git commit/push。真实服务器认证后的 App 操作应由用户在手机上继续验收；本地 API 测试覆盖了认证 CRUD 与账号隔离。

### 手机验收建议

安装 `app/build/outputs/apk/debug/app-debug.apk` 并用现有账号登录：

1. 新建对话，问“推荐南京景点”，再问“美食呢？”，确认第二问沿用南京；切到新对话问“美食呢？”，确认不会继承旧对话的南京。
2. 退出并重开 App，打开刚才的对话，确认消息仍在；删除该对话后确认列表消失。
3. 在聊天中说“记住我不吃辣”，确认成功提示；到个人中心确认偏好可见，再新建对话验证偏好仍在。
4. 删除刚才保存偏好的那条聊天，确认个人中心偏好保留；在个人中心删除偏好，确认它不再显示。也可在聊天中说“忘记我不吃辣”验证主动删除。
5. 发送“我朋友不吃辣”或“这次不吃辣”，确认这类话不会被保存成长期偏好。

会话隔离、摘要触发、边界输入和跨用户权限已由自动化测试覆盖；不用为了触发压缩在手机上手工发送大量消息。两台设备同步可在有第二台设备时补测。
