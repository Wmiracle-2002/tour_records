# Agent 功能与高德 API 改进方案（讨论稿）

日期：2026-09-25
目标：稳定回答个人旅行历史、文字旅行规划、距离、天气与预算；取消具体路线导航。

## 一、逐项功能和 API

| 功能 | 必需数据与高德 API | 输出约束 |
| --- | --- | --- |
| 去过哪里、哪些景点和美食 | 只查当前登录用户的 SQLite 旅行、景点、美食记录；**0 个高德 API** | 按城市、类别、时间等条件回答；查无记录明确说没有。高德地点不能算本人去过。 |
| 按天规划景点和三餐 | **POI**（兴趣点，即高德收录的景点/餐饮地点）：`GET /v3/place/text`，分别搜索目的城市的景点和餐饮 | 有日期时显示 x月x日，未给日期时显示第 N 天。上午/下午/晚上安排景点，早餐/午餐/晚餐推荐美食；不强求精确分钟。 |
| 两个地点相距多远 | `GET /v3/place/text` 为起终点定位并取得高德坐标，然后 `GET /v3/distance` | 默认给明确标注的**直线距离**；明确问驾车/步行距离时才选相应模式。不返回转弯指令或导航路线。 |
| 当前或某日天气 | `GET /v3/config/district` 将城市/区县解析成高德 adcode，然后 `GET /v3/weather/weatherInfo` | 只对实况或返回预报日期范围内的日子回答；不拿今日天气代替指定日期。 |
| 旅行预算估计 | 服务端本地预算估算，可参考本人历史花费；**0 个高德 API** | 给人民币粗估区间和天数、人数、住宿/餐饮/交通等假设；不冒充实时价格。 |

共需 **4 种高德 Web 服务接口**：POI 关键字搜索、距离测量、行政区域查询、天气查询。地理/逆地理编码、周边搜索、POI 详情，以及步行/驾车/公交/骑行**路线**接口不参与本版 Agent；距离数值问答仍保留。

官方文档：[POI 搜索](https://lbs.amap.com/api/webservice/guide/api/search/)、[距离测量](https://lbs.amap.com/api/webservice/guide/api/direction)、[行政区域查询](https://lbs.amap.com/api/webservice/guide/api/district)、[天气查询](https://lbs.amap.com/api/webservice/guide/api-advanced/weatherinfo)。只用服务端 Web 服务 Key 和 HTTPS GET，固定 `output=JSON`；LLM 不负责拼接高德 URL、Key 或服务商参数。

## 二、逐接口精确参数及限制

### 1. POI 关键字搜索

端点：`GET https://restapi.amap.com/v3/place/text`。

| 参数 | 高德文档规则 | 本项目发送前的更严格限制 |
| --- | --- | --- |
| `keywords` / `types` | 至少一个非空；`types` 为官方分类代码或名称，多值可用 `|` 分隔 | 先只发单个非空 `keywords`；规划的景点/餐饮查询词由后端固定，测距时用规范化地点名。LLM 不填写六位类型代码。 |
| `city` | 城市中文名、citycode 或 adcode；只填 `city` 不保证结果仅在该城 | 本项目必填已确认的城市名称或经高德核对的 adcode，不直接使用未核对的统计局城市编码。 |
| `citylimit` | `true/false`，默认 `false` | 固定 `true`，并再次核验响应的城市归属。 |
| `page`、`offset` | 页码从 1 开始；官方强烈建议 `offset ≤ 25` | 固定 `page=1`、`offset=10`，翻页另行做有界处理。 |
| `extensions` | `base/all` | 固定 `base`。 |

景点和美食分别搜索，不能把所有泛词搜索结果直接当成正确类别。响应必须有成功的 `status/infocode` 和列表 `pois`；逐项核对 `id/name/type/cityname/adcode`，测距还必须有合法 `location`。过滤跨城、类型明显不符及重复项。泛词质量不足时用实际返回数据核验查询词/官方分类表，再确定后端允许的 `types`；不让 LLM 猜类型。接口不保证可靠开放时间、门票价或营业状态，不能宣称这些已验证。

### 2. 距离测量

端点：`GET https://restapi.amap.com/v3/distance`。

| 参数 | 高德文档规则 | 本项目发送前的更严格限制 |
| --- | --- | --- |
| `origins` | 1～100 个 `经度,纬度` 坐标对，多个用 `|` 分隔 | 单次文字问答只用 1 个已确认 POI 的坐标，绝不传“中山陵”等地点名。 |
| `destination` | 单个 `经度,纬度`；小数最多 6 位 | 只用已确认终点 POI 的高德坐标，小数最多 6 位。 |
| `type` | `0` 直线；`1` 驾车导航距离（仅国内，考虑路况）；`3` 步行规划距离（仅支持 5 km 内）；默认 `1` | 总是显式发送：未指定方式用 `0`，明确驾车用 `1`，明确步行且预检在支持范围内才用 `3`；回答标明方式。 |

先在用户指定的同一城市分别搜索两个地点，再按名称、类别、城市和 POI ID 选出**唯一**结果；同名异地或缺少城市时澄清，不拿首条猜测。坐标必须是有限数，纬度 `[-90,90]`、经度 `[-180,180]`，采用高德返回的坐标系；不可混入其他坐标系。步行查询可用两点直线距离做保守上限预检，接近或超过 5 km 时不调用 `type=3`，可以改为明确标注的直线距离。检查顶层 `status/infocode`、对应 `results` 条目的 `info/code` 和非负米数；驾车结果会随路况变化，不能说成固定值。

### 3. 行政区域查询

端点：`GET https://restapi.amap.com/v3/config/district`。

| 参数 | 高德文档规则 | 本项目发送前的更严格限制 |
| --- | --- | --- |
| `keywords` | 只支持单个行政区名称、citycode 或 adcode | 只发一个已解析的行政区名；“南京|苏州”等拼接值无效。 |
| `subdistrict` | `0` 不返回下级行政区 | 固定 `0`。 |
| `extensions` | `base` 不返回边界点；`all` 返回边界点 | 固定 `base`。 |
| `page`、`offset` | 最外层 `districts` 单页最多 20 项 | 固定 `page=1`、`offset=20`；匹配不唯一时不猜第一项。 |

根据响应 `districts[].name/level/adcode` 与用户城市及省份上下文确定唯一结果。直辖市在高德响应中可能是 `province` 层级，不能只接受 `city`；区县问题应使用相应区县编码。天气的 adcode 必须来自高德并经核对，不能假定 Android 现有的国家统计局 2023 编码与高德始终一致。实施时为服务端建立只读城市名称/别名索引，处理“南京/南京市”等写法；允许缓存已核对的高德 adcode。

### 4. 天气查询

端点：`GET https://restapi.amap.com/v3/weather/weatherInfo`。

| 参数 | 高德文档规则 | 本项目发送前的更严格限制 |
| --- | --- | --- |
| `city` | **必填高德 adcode** | 只允许前一步确认的六位 adcode；不传“南京”等名称。 |
| `extensions` | `base` 实况、`all` 预报 | 根据解析后的**时间需求类型**选择：问此刻实况用 `base`；问今天全天、今晚、明天、某个日期或未来几天用 `all`。|

先将用户问法规范化为 `realtime`、`forecast_date`、`forecast_range` 或 `ambiguous`，由后端再确定参数。例如“此刻/目前/现在南京冷不冷”是实况；“今天南京天气怎么样”默认问今天全天预报，“今晚会下雨吗”取今天的夜间预报，“明天/中秋南京天气”是指定日期预报；仅说“南京天气怎么样”时可以返回**明确标注为当前实况**的结果，并提示若想看某天预报请给日期。时间范围按服务端的中国时区确定；不能把提到“现在”的“从现在到明天”误判为只有实况。官方 `casts` 通常按当天至第四天排列，但必须按**实际返回的 `casts[].date`**匹配目标日期/范围，不能认为一定有四天数据。“中秋”“国庆”等自然语言时间先转换成带年份的公历日期；年份不明且无法根据上下文唯一确定时先澄清。日期超出高德预报、响应为空或 adcode 不匹配时明确说明无法回答，不回退到当日天气。响应校验 `status/infocode` 与 `reporttime`。

### 5. 本地预算

预算不经过高德。复用本地估算工具，严格转换天数/人数为正整数、人民币金额为非负数，限制极端值；缺少关键信息时说明默认假设或澄清。输出人民币区间与明细，并明确“粗估”；POI 搜索结果不能当实时餐费/门票价格。

## 三、两道硬约束

**调用前的业务转换：** LLM 只提取意图、城市、地点名称、天数/日期、天气时间需求类型、测距方式、人数与预算等业务字段。服务端统一字段名和类型；城市通过只读索引及高德行政区响应核对，地点经限城 POI 搜索转换为唯一 POI 与坐标，节日/相对日期转换为带年份的公历日期，天气时间需求类型按固定枚举校验。缺失、歧义、不合业务范围时澄清；“国庆”不直接作为 ISO 日期，“中山陵”不直接作为坐标。历史查询的用户 ID 只能来自服务端身份认证。

**发送高德前的端点校验：** 为上述四种接口分别定义只含允许字段的严格请求模型。检查必填项、枚举、坐标顺序/精度/范围、adcode 来源、数量及页码；失败时**不发送请求**。高德响应先检查 `status/info/infocode`，再检查端点特有的 POI、城市、日期、距离数据；错误以明确状态返回，不交给 LLM 填补。日志记录 request_id、业务参数、选点依据、端点、耗时和高德错误码；不记录 Web 服务 Key 或认证令牌。

Prompt 可给正反例，但只是软约束。安全的别名和格式可自动修正一次；仍不合规时按[Agent 参数模型修正方案](Agent参数模型修正.md)最多让 LLM 重试一次，之后受控失败，避免无限工具循环。

## 四、Agent 流程与规划形式

```text
消息 → 意图和业务字段解析 → 后端转换/校验
  ├─ 旅行历史 → 本人 SQLite → 有依据的事实回答
  ├─ 行程规划 → 限城景点 POI + 餐饮 POI + 可选本人历史/预算 → 时段行程 → 硬校验
  ├─ 距离 → 两端 POI/坐标 → distance → 标注方式的文字距离
  ├─ 天气 → 日期/城市 → district/adcode → weather → 对应日期天气
  └─ 预算 → 本地估算 → 标明假设的预算区间
```

保留 LangGraph 主流程，移除路线导航工具的 Agent 调度。上述已确定的调用链由后端按意图选择工具，减少多轮 ReAct 随机生成参数与总耗时；限制候选数、工具次数、LLM 重试与整体超时。历史回答只使用用户记录，避免把“去过南京哪些景点”退化成“去过哪些城市”。

规划模型从 `start_time/end_time` 改为**日期/日序号 + 景点时段（上午/下午/晚上）+ 用餐时段（早餐/午餐/晚餐）**。给了可解析的出发日才显示 x月x日；否则写第 N 天。每个具名景点、餐馆须引用合格 POI 或本人记录；候选不足时留空并说明，不编造地点。硬校验天数、日期、时段枚举、POI ID、城市、类别与同日重复。开放时间和实际价格在末尾统一提醒核实，不逐项报“路线/开放时间未验证”。天气、距离和预算可独立问答，也可作为规划补充；它们的故障不阻断已有可靠 POI 的基本行程。

## 五、实施顺序和逐步回归

| 步骤 | 代码工作 / 完成标准 | 每步回归重点 |
| --- | --- | --- |
| A. 业务模型 | 统一城市、地点、日期字段；行程支持日期/日序号及六个粗粒度时段；路线导航不再调度 | 历史城市/景点/美食分类和用户隔离；无日期不造日期；路线问题明确告知不提供导航。 |
| B. POI 边界 | 搜景点、餐饮和测距端点共用严格 POI 请求/响应校验 | 捕获实际 `params`；空词、错城、同名、无坐标、跨城、错误码时不生成伪地点。 |
| C. 距离、天气 | 两端 POI → 距离；天气时间需求分类 + 城市 → adcode → 实况或对应日期预报 | “中山陵到夫子庙”、驾车/步行 5 km 边界、异城同名；“此刻/今天/今晚/明天/中秋/从现在到明天”的模式和日期边界；非法请求断言不联网。 |
| D. 预算与行程 | 保留人民币粗估；按每天三段景点与三餐输出，压缩 LLM 决策轮数 | 1～3 日、避开去过地点、候选不足、预算边界、LLM 格式错/超时的受控降级。 |
| E. 联调和文档 | 服务端模拟 Android 消息，核对调用日志、响应及耗时；更新 README/Agent 稳定性计划 | 五类问题逐项回归；任何降级均不编造历史、地点、天气或价格。 |

每步完成后跑相关单元测试、Agent API 测试和现有回归，再进入下一步。有 Key 的环境再做真实高德联调；无 Key 时用 HTTP 假响应验证最终发出的参数。方案成功标准：五类问答可稳定输出，四类高德请求符合官方约束，具体路线不再触发，规划不再因冗余工具轮次拖到超时。
