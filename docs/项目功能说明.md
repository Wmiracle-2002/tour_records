# 足迹项目功能说明

更新日期：2026-09-30。本文描述当前代码已实现的功能；个人旅行知识库开发范围见 [Agent 开发计划](Agent开发计划.md) Phase 17。

## 1. 产品定位与使用方式

足迹用于记录个人旅行，并用对话查询自己的旅行经历、获取目的地信息和生成粗粒度行程。Android App 有“记录、智能规划、个人中心”三个底部入口。可仅用本地 Room 数据库体验记录功能；登录账号后，旅行记录、对话和偏好由个人服务器提供，手机保留可浏览的记录缓存。服务端采用 FastAPI、SQLite、Alembic，外部能力包括大模型、高德 Web 服务和腾讯云 COS。

本地模式与云端模式是两种数据来源。现有实现不自动将旧本地旅行上传到账号；有未同步本地旅行时会阻止登录，以免将两套数据混在同一时间线。云端写操作需要服务端可用，断网时只可浏览已缓存的云端记录。

## 2. 旅行记录

| 对象 | 内容与行为 |
| --- | --- |
| 城市 | 新建旅行选择地级目的地、直辖市及无地级上级的省直管县级市。离线行政区划数据来自 2023 年公开数据；区县名可用于搜索上级城市。 |
| 旅行 Trip | 城市和实际出行起止日期；同一城市可以建立多次不同时段的旅行。记录页按时间展示，统计去过的城市数与出行次数。 |
| 子记录 Record | 在旅行内添加景点或美食，填写实际日期、名称、可选评分、可选人民币花费、备注与照片；日期须落在旅行区间内。支持详情、编辑和删除。 |
| 照片 | 本地模式使用系统照片选择器，压缩为长边 1080px、JPEG 质量 80，并保存到 App 私有目录；每条记录最多 9 张。删除记录时清理本地照片。云端模式上传原图至 COS，服务端保存图片元数据与访问地址；删除云端照片或记录时清理关联对象。 |
| 账号与缓存 | 账号通过用户名/密码登录，业务请求使用 Access Token，过期后可用 Refresh Token 刷新。云端写入成功后刷新 Room 缓存；个人中心可手动刷新其他设备的变更。 |

当前部署的账号由服务端初始化脚本预先创建，App 尚不提供自行注册。两个人可以登录同一个账号查看同一份旅行数据；不同账号的数据在服务端按用户 ID 隔离。

Android 本地表以 `City → Trip → Record` 组织。服务端以 `User → Trip → Record → RecordImage` 组织，并按用户 ID 限制业务读取与修改。个人中心还展示旅行统计、总花费、账号状态和长期偏好管理。

## 3. Agent 能回答什么

- **旅行历史**：只问城市时仅列城市；问去过的地方时按城市列景点，问吃过的美食时按城市列美食，明确同时询问时分列两类。同城多次旅行合并展示、同名去重；仅以当前账号的 Trip/Record 为事实来源。没有去过时明确说明，不虚构经历。
- **目的地推荐**：按城市查询景点或餐饮 POI。服务端用明确的城市与类别约束高德结果，过滤错城、错类、重复项及无效坐标。
- **天气**：区分“现在/当前”的实况与“明天/后天/指定日期”的预报；先核对城市行政编码，超出预报范围或日期不明确时说明限制。
- **距离**：先解析起终点 POI，再用有效坐标测距；默认给直线距离，按明确要求可给驾车或步行测距。当前不提供导航路线展示。
- **预算**：以人民币给出粗略预算和中文费用分类；不是实时票价或订房报价。
- **旅行规划**：按天安排早餐、上午、午餐、下午、晚餐、晚上，组合已核验的景点与餐饮候选，考虑用户明确限制、旅行历史、长期偏好与同城个人收藏。可用事实不足时保留空时段或解释缺口，不编造开放时间、门票或地点；采用收藏时给出标题及编号。

个人收藏是登录用户主动录入的笔记、旅行攻略、美食攻略和景点攻略，支持城市/关键词查找、详情及增删改。它与旅行历史、会话和长期偏好分别保存；删除会话不会删除收藏。规划仅按目的地取少量摘录，不能把旧攻略中的营业时间、价格、天气当作实时事实，也不能把未核验的地点直接放入行程。当前没有公共网页搜索或向量检索。

## 4. Agent 执行链路

```text
Android 消息 → FastAPI 鉴权、会话/消息去重
             → LangGraph 需求分析（结构化 TravelRequirement）
             → 信息状态初始化与收集（内部旅行记录、高德、预算）
             → 事实问答 / 行程生成 → 行程校验 → 必要时局部修订
             → 最终回答 → 会话持久化 → Android 展示
```

LangGraph 根据意图选择事实问答或旅行规划分支；ReAct 收集器受轮次和信息状态约束，避免已完成的信息反复查询。规划分支先获取景点和餐饮候选，再生成结构化 `Itinerary`。Validator 检查候选来源、类别、重复、日期及硬约束；Reviser 在限定轮次内调整。外部事实缺失时走受控降级或提示缺口。LLM 负责理解与生成，但不能自行拼接高德 URL、传入任意数据库用户 ID 或把未验证地点直接写入最终行程。

工具层采用统一注册、输入模型校验与 `ToolResult` 状态。参数先做安全归一化，再经严格模型和高德接口边界校验；失败会形成明确错误，必要时允许有限重试。高德 Key、LLM Key 和 COS 凭据只存于服务端环境配置。使用中的主要高德能力为 POI 搜索、行政区查询、天气与距离测量；路线导航已从当前产品能力中移除。

## 5. 记忆与会话

每个登录账号可建立、切换、查看、删除多个会话；历史消息落盘到 SQLite，`client_message_id` 用于同一消息重试去重。短期上下文由三部分组成：完整原始消息、当前话题/已确认条件的结构化会话状态、受预算限制的近期问答。最近最多 8 轮只是候选窗口；约 6000 token 的估算预算仍会裁剪输入。

未压缩历史接近记忆预算的 70% 时，早期消息按区间分块摘要，原文继续保存；必要时可在当前用户、当前会话范围内回查原文。工具调用记录规范化参数、状态、摘要和完整结果引用，每种工具最多选取 2 条相关概述进入上下文，明确需要时可回查原始结果。长期偏好与会话独立，目前只响应用户明确的“记住/忘记”命令或个人中心编辑；删除会话不删除偏好。旧天气、POI、价格不会因记忆存在而当作当前事实复用。摘要和 token 数均为估算，不能保证自动找回每条旧信息。

## 6. 接口、流式交互与可观测性

| 范围 | 主要接口 |
| --- | --- |
| 认证 | `POST /api/v1/auth/login`、`POST /api/v1/auth/refresh`、`GET /api/v1/auth/me` |
| 旅行 | `/api/v1/trips`、`/api/v1/trips/{id}`、`/api/v1/trips/{id}/records`、`/api/v1/records/{id}`、图片上传/查询/删除、`GET /api/v1/stats` |
| Agent | `POST /api/v1/agent/chat`（完整 JSON）、`POST /api/v1/agent/chat/stream`（SSE）、会话列表/消息/删除、长期偏好 CRUD |
| 个人收藏 | `POST/GET /api/v1/agent/knowledge`、`GET/PATCH/DELETE /api/v1/agent/knowledge/{id}`；均需登录，按账号隔离 |
| 健康 | `GET /api/v1/health` |

SSE 返回 `started`、公开的 `stage`、逐日校验后的 `preview`、最终正文 `content`、`completed` 或 `error`。多日规划时，模型流式生成 JSON；每完成一天并通过已有景点、日期、时段等规则检查，就以 `preview` 更新生成中的回答。整份行程仍执行原有 Validator/Reviser，`completed` 与持久化内容才是最终答案；先前预览可能在总校验后被替换。短问答可能一次性返回。流已建立后即便发生错误，HTTP 可能是 200，客户端仅以 `completed` 判断成功；断线或失败不保存半截助手回答。

FastAPI middleware 生成或接收 `X-Request-ID` 并记录 HTTP 状态、耗时和结果；Agent 日志记录各阶段、工具调用与耗时，便于关联 Nginx、API 与上游调用。工具业务参数可在服务端开发日志中追查，API Key 不写入日志。接口参数与用户归属由服务端校验。总执行时间、阶段时间和 ReAct/修订次数均设有上限，超时或外部服务故障返回明确错误或受控降级。

## 7. 部署与当前边界

本地开发需 JDK 17、Android SDK 34、Python 3.12；服务端也可用 Docker Compose 运行，SQLite 数据持久化在服务端，Nginx 提供 HTTPS 入口。配置示例在 `server/.env.example`，应用安装和回归步骤见 [测试指南](测试指南.md)。

截至 2026-09-30：个人旅行收藏服务端迁移与真实 HTTP CRUD/隔离已验收，Android Debug APK 已构建；真机收藏界面、实际 LLM 规划引用和流式体验仍待用户验收。API 24 最低版本、第二台真实设备和弱网场景仍需回归。模型回答质量、天气预报范围、POI 数据和 COS 可用性取决于外部服务，不能把自动化测试等同于长期线上可靠性。更多历史决策见 [Agent 架构](Agent架构.md)、[记忆方案](Agent记忆系统方案.md)和 [开发日志](开发日志.md)。
