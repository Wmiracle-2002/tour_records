## P01 技术失败：目前没有行程可复核

- 请求ID：`4102f6af749844b3ac32fd6eebcb7fc5`。需求提取南京、一日正确，景点和餐饮快照均返回；随后生成阶段抛出`sqlite3.OperationalError: database is locked`，SSE error.code=500。
- 源码证据：`ConversationMemoryService.record_tool_run()`保存工具运行记录后只flush，持有未提交的SQLite写事务；之后LLM transport通过独立Session执行`TokenQuota.reserve()`，第二个写事务无法取得写锁。
- 离线复现：分别使用DELETE与WAL日志模式，额度预留在工具写入前成功；工具记录未提交时稳定报锁；回滚该事务后额度预留恢复。此复现不调用模型，表明不能只用提高超时或开启WAL解决。
- 本轮保留失败，不绕开额度或提前提交来伪造规划成功。后续优先修复工具结果持久化与额度账本的事务边界，并增加两者同时启用的回归用例，再重测P01后请用户验收行程。尚未把该修复部署到生产。

## 2026-10-08 用户反馈后的修复与复测

以上为首次试跑的历史记录，保留原始答案与失败；本节为后续修复。用户已明确：只问城市就只回答城市；“去过的地方”仅指景点，按城市分组；吃过的美食单独按城市分组。H01 的补充地点清单现属于不符合产品要求，不能继续仅视为可接受的冗长。

### 修改原因与实现

- 归一化原先只有扁平的 visited_names，丢失城市与记录类别的对应关系。现在保留 `records_by_city`，用数据库已有的 ATTRACTION/FOOD 分类生成答案；同城多次旅行合并、同名去重，不从名称猜类别。
- 需求分析增加明确问法的规则校正；查询参数以分析后的城市和类别为准，避免 ReAct 再选错。明确同时问景点和美食时使用 BOTH，数据库查询不传 BOTH，展示时分别列出两类。
- 修复无标点的“我去过哪些城市/地方”被城市兜底正则误提取的问题。未知城市、空记录继续明确说明，不补造记录。
- 工具执行追踪保存后，由运行时提交短事务；会话压缩完成后也先提交，再进入下一次 LLM 调用。追踪记录独立持久化，后续生成失败仍可排查；不再跨 LLM 调用持有 SQLite 写锁。
- 首次修复后 P01 恢复返回，但漏了明确要求的晚间安排。新增已明确时段的完整性检查：对应类别有至少三个已核验候选时，缺少要求的时段触发已有的一次修正重试；候选不足不强行编造。逐日预览采用相同检查。
