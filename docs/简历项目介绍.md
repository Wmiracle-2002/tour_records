# 足迹 Travel Agent｜简历项目介绍

以下内容按当前代码与已完成测试编写。项目定位为个人项目；Android 客户端由本人结合 AI 工具开发，简历重点放在熟悉的 Python 服务端和 Agent 系统设计。

## 可直接放入简历的版本

**足迹（Footmarks）｜个人旅行 Agent 项目｜Python / FastAPI / LangGraph / Pydantic / SQLite / 高德 Web API**

面向个人旅行记录构建多轮对话 Agent，支持查询去过的城市、景点与美食，获取目的地 POI、天气、距离和预算信息，并生成按天及上午/下午/晚间、三餐组织的行程。Android 客户端结合 AI 工具完成，用于记录旅行和验证 Agent 交互。

- 设计 LangGraph 状态图：将需求分析、信息收集、事实问答、结构化行程生成、规则校验、局部修订和最终回答拆成明确节点；以意图分支、信息状态、最大轮次及超时预算控制流程，避免无效循环和无限等待。
- 建立受约束的工具调用层：用 Pydantic 模型校验工具输入，统一成功/不可用/失败结果；服务端规范化城市、POI 类型、日期与坐标后调用高德 POI、天气、行政区和距离接口，过滤错城与无效候选，降低 LLM 参数错误和虚构地点风险。
- 实现会话记忆：在 SQLite 持久化完整原文、结构化当前话题、近期上下文、区间摘要及工具调用索引；以记忆预算 70% 为压缩触发阈值，并支持按用户和会话隔离的原文/工具结果回查。长期偏好仅在用户明确要求时保存，避免把临时条件误写为永久偏好。
- 提供 FastAPI 认证接口与 SSE 响应：在行程校验通过前只推送公开阶段进度，校验后分段发送正文；通过 `client_message_id` 去重、断线取消和请求 ID 关联 HTTP、Agent 阶段与工具日志，支持定位超时及上游错误。
- 建立自动化回归：服务端 Phase 16 全量 459 项测试通过，覆盖 Agent 图、工具边界、会话/偏好隔离、流事件、失败与断线；Android JVM 测试及 API 34 模拟器 50 项仪器测试通过。真实手机的流式问答仍待验收。

## 面试讲述要点

1. **为什么用状态图**：旅行规划不是单次提示词。先确定用户意图，再查可信数据、生成行程、验证约束；状态图能显式控制条件分支和修订循环。事实查询与规划分流，可减少不必要的模型调用。
2. **如何控制幻觉与参数错误**：LLM 只提出结构化需求和候选动作；工具参数通过严格模型与业务规则，高德结果再次校验城市、类别及坐标；行程只能引用已收集候选，没有证据就说明缺口。
3. **长对话如何兼顾上下文与成本**：完整消息始终留在 SQLite；模型只接收当前结构化状态、近期问答和相关摘要。超阈值时摘要旧区间，必要时按受限 ID 回查原文与工具结果，不把过期天气或价格当作新事实。
4. **流式输出的真实边界**：先实时推送执行阶段，最终正文经校验后再分段到达；这比直接暴露未经验证的模型 token 更适合结构化行程。可说明下一步是按已验证日程分阶段生成，而当前版本尚未做到真正 token 级输出。

## 表述边界

- 不写“RAG/向量数据库/知识库已上线”：个人攻略知识库在 Phase 17 计划中，尚未实现。
- 不写“模型 token 级实时流式生成”：当前实时的是阶段进度，正文在最终校验后分段发送。
- 不写虚构的响应速度提升、准确率或用户规模；已有的测试数量是本地自动化结果，不等同于真实手机或长期线上指标。
- Android 端可写“结合 AI 工具完成客户端并进行联调”，无需把 Kotlin/Compose 作为个人熟练技术栈。
