# Agent零Token分阶段评测与指标审查

日期：2026-10-09。用户要求Token不足，后续评测不调用真实LLM。本次仅读取既有JSON、运行本地判分器；不调用API、不修改服务器或原始结果。

## 100%的解释与已确认缺陷

以前公布的分数是已知回归题上的受限指标，不能解释为Agent对真实用户问题的准确率。题库参与了修复、没有独立留出集；合成工具数据缺少噪声、歧义与真实接口失败。105个意图标签只有35个独立消息步骤，156个槽位标签只有52个独立字段检查，都是同题重复三轮，不是105/156个独立新样本。

现有`model_outputs`在结构化客户端校验后保存，不能据此估计原始首个HTTP返回的JSON格式正确率；之前意图/槽位读取最终需求模型，还含程序后处理。不能把解析成功当成用户需求理解正确。

### 零Token判分器反例审查

仅深拷贝原始结果并注入明显错误的回答，原始文件不变。保留原需求和工具证据，测试判分器能否检测回答与这些证据矛盾：

| 用例 | 注入的明确错误 | 原判分器 |
|---|---|---|
| R01 | 将中山陵、夫子庙、玄武湖推荐后说“以上都位于上海” | 错误地pass |
| M05 | “你没有说过预算2000元，也没有说过不想去寺庙” | 错误地pass |
| W05 | “12月1日可以查询，近期预报覆盖全年” | 错误地pass |

三个针对性反例全部漏检。这里只证明判分器存在漏洞，**不是判分器真实误判率100%，也不是Agent实际生成了这些错误回答**。主要原因是关键词匹配不处理否定/矛盾。另有两个已确认问题：knowledge_citation仅检查轨迹非空，没检查正文引用；unknown_facts_disclosed以数字字面禁止导致正确引用旧笔记也被误判。

因此旧自动规则只能作为结构/流程诊断，不能承担完整答案质量评分。不要人为调低分数，要增强参考标注、覆盖和独立性。

## 零Token评测的三种方式

1. **既有运行日志重新评分**：使用已保存的结构化输出、工具结果、记忆与状态，人工或确定性规则核对。能衡量那一版模型在那一批题上的表现，不能得到修改后模型的新行为或新推理耗时。
2. **注入固定LLM返回并执行真实程序链路**：把合法/非法JSON、错误参数、错误行程、超时和重复回复作为固定输入，检查参数修正、重试、工具调度、数据库隔离、校验与格式化。测的是程序可靠性，不能称为LLM准确率或端到端模型成功率。
3. **独立模块评测**：为检索、记忆读写、规则校验、工具参数转换等准备人工gold，通过SQLite和假工具响应离线运行。能够测这些模块，不需要LLM。

后续默认关闭网络/注入遇到未记录请求即抛错的LLM客户端；每份离线报告记录real_llm_calls=0。不用真实模型生成新样本或作为评分裁判。现有`run_full.py`默认会调用模型，只有`--offline-check`模式允许在当前预算下运行；该模式只检验数据预置/隔离，不是质量评分。

## 下一轮离线评测顺序与验收

1. 审查并修正判分器：保存旧版，新增版本；上述三种矛盾反例必须判失败，正确引用旧笔记必须能与现行事实区分。判分器自身使用独立正常/错误答案标注，报告错误检测Precision/Recall/F1；不为降低100%而加入没有事实依据的扣分。
2. 建完整gold侧文件：意图与全部槽位、工具轨迹、相关记忆与笔记、行程错误类型和答案支持证据；采用过程与最终答案均单独判分。原题库作为回归集，不当留出集。
3. 模块测试集分正常、边界、异常、对抗；记录每组样本数与独立题数，固定规则及随机种子。gold手工定义，不从待测程序预测值自动生成。调试集与验收集分离。
4. 在禁止LLM/外网的环境运行参数处理、检索、执行、校验、状态和展示；生成分阶段报告。出现100%可以保留，但必须给出样本范围、错误覆盖和已知限制。
5. 用旧日志重新计算模型相关指标和历史性能；最新模型泛化、真实端到端TSR、真实API/QPS/首Token延迟留为未评测。预算恢复后才考虑真实模型留出题，不自动调用。
