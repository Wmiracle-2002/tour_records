# Agent 评测方案

日期：2026-10-08；题库版本：`core-v1`。目标是得到可复现的任务质量、响应性能与调用成本数据，为项目改进和简历提供证据。

## 1. 本轮交付与范围

方案首版生成40个核心场景、合成标准数据、结果模板和题库检查脚本。后续已实现隔离装载、故障注入、HTTP/SSE运行器、规则判分与人工复核导出；截至2026-10-09，服务器40场景试跑和正式三轮141条消息已完成。结果见[全量评测报告](Agent全量评测报告-2026-10-09.md)，自动初判不能替代最终语义正确率。

文件位于 `server/evaluation/`：

- `cases.json`：固定输入、会话步骤、预置条件、逐步通过标准与禁止行为。
- `fixtures.json`：两个隔离账号的旅行、偏好、收藏，以及冻结日期、合成 POI/天气/距离快照。
- `results-template.csv`：每场景、每次重复、每个步骤的原始结果记录模板；空白不代表通过。
- `validate_cases.py`：检查数量、编号、数据引用、步骤类型、规则结构和结果模板，不调用业务服务。
- `README.md`：使用方法与当前实施边界。

首批分配：历史 8、推荐 7、天气 5、距离 4、预算 3、规划 6、记忆 5、异常 2，共 40 个场景。每个场景重复 3 次；多轮场景的每次重复从独立会话和账号数据快照开始。后续扩到 120 个场景时保留本批为回归集，新增独立保留集，避免只针对已知题目优化。

人工阅读清单见 [Agent评测用例](Agent评测用例.md)。本批共 47 条消息步骤，三次重复为 141 条消息；38 个正常业务场景与 2 个故障场景分开计分。

## 2. 两条评测轨道

### A：真实 LLM + 固定数据

使用真实模型分析、决策和生成；仅将高德与数据库数据固定。不能把假 LLM 的正确输出算成模型准确率。冻结北京时间为 `2026-10-08T10:00:00+08:00`，同步替换需求分析、相对日期和记忆代码读取的时间入口；确认无残留系统日期后才运行日期题。

A 轨耗时仅代表固定数据条件下的模型与内部链路开销，不能当作真实高德网络性能；对外描述端到端性能时使用 B 轨结果，明确服务器、模型和运行条件。

标准数据中的 POI ID、天气与距离均为合成值，只用于评测，不可当作实时旅游事实。固定快照需通过工具提供者适配器返回符合现有接口的数据结构，且仍经过项目原有参数校验、归一化和规则校验。规则中使用标准名是语义核对；除 ID、枚举和数字外，不要求模型逐字复述。

### B：真实 LLM + 真实外部服务

通过与 Android 相同的 JSON/SSE 请求结构访问 API；记录实际工具参数及返回快照，再核对城市、日期、类别和最终答案。天气按运行当天重算，距离按本次工具返回判分，不与 A 轨合成值比较。无匹配 POI 时的诚实降级可满足可靠性规则，但不等于推荐完成；任务完成与安全降级分别统计。

两条轨道分开报告，不能混合平均。故障注入和账号隔离在独立测试环境执行，不修改生产账号、真实用户历史或生产服务配置。本轮 `core-v1` 的 40 个场景均只声明 A 轨，结果模板也仅列 A 轨。B 轨后续另生成适配题库：天气题随运行日改日期，距离和推荐以实际工具快照取代合成值；不能直接照搬 A 轨判分值。

## 3. 判分规则

每一步的 `required` 均为必需条件，任一失败则该步失败；`forbidden` 命中任一项同样失败。一个场景所有计分步骤通过才算任务成功。新建会话、数据预置等准备步骤不计入回答准确率；准备失败记为运行无效，说明原因后整场重跑，不能当成模型失败或偷偷删除。

判分使用三种证据：

1. **程序规则**：解析需求模型、工具调用轨迹、结构化行程、数据库状态和 HTTP/SSE 事件。按城市/POI ID/类型/日期/金额比较，不用关键词匹配替代语义判定。
2. **人工复核**：核对最终回答是否切题、是否存在无依据断言、规则难表达的限制是否满足。模型输出与轨迹交叉核对；规划合理性按 0～2 分评分：0=明显违背要求或不可用，1=基本可用但安排较弱，2=符合要求且组织清楚。该分单独报告，不与硬规则混为准确率。
3. **LLM 辅助评分**：可辅助标注，但首版不开启；不能让被测模型自行判定自己正确。争议题由用户复核，保留原判、复核结论和原因。

推荐题须返回至少一个符合要求的真实候选才能算完成；规划题要求规定天数和时段、餐饮覆盖且不得使用未核验地点。不能通过留空所有时段来取得高约束满足率。B 轨资料不足时分别记“安全降级”和“任务未完成”。路线导航不属于当前支持功能，不设置成功导航的题目。

## 4. 按模块使用常见指标（2026-10-09 修订）

评测既要判断整项任务是否完成，也要定位具体模块的问题。对外报告采用常见指标及明确计算口径，内部合法性、覆盖率检查只用于诊断。完整定义、现有证据和未评测项见 [Agent评测指标修订](Agent评测指标修订.md)。

| 模块 | 主指标 | 如何评测 |
| --- | --- | --- |
| 需求理解 | Intent Accuracy；Slot Precision / Recall / F1 | 人工标注意图及完整槽位集合，按字段和值匹配。现有题库只有部分槽位标签，暂报显式标签的 Exact Accuracy，不能冒充完整 F1。 |
| 工具调用 | Tool Call Accuracy / F1 | 参考工具名、参数和必要调用；允许标注等价路径。正确选择但参数错误不能算正确，参数合法也不代表调用正确。 |
| 规划 | Task Success Rate（TSR）；Constraint Satisfaction Rate | 按最终行程核对天数、时段、忌口、排除地点、去重、收藏依据；整项约束全部满足与逐约束结果分别说明；合理性另人工复核。 |
| 记忆 | 事实 Exact Match / F1；检索 Recall@K | 核对已保存/应回忆事实；为历史消息标注相关性，检查前 K 条检索是否找回。只触发压缩不表示记忆正确。 |
| 知识库 / RAG | Context Precision / Recall；Faithfulness | 标注检索内容相关性、参考事实覆盖及答案各事实是否受证据支持。引用笔记并不自动等于忠实；过时信息不得当作当前事实。 |
| 整体 Agent | Task Success Rate；重复运行可靠性 pass^k | 一个多轮任务的全部目标与禁止条件都满足才成功；缺测/内部失败算失败。正常任务与故障注入分开统计。三轮实测稳定率需有真实成功标签，自动规则三轮全过仅是诊断。 |
| 性能与成本 | P50 / P95 latency；Tokens / task；LLM calls / task | 按同一模块、场景和轨道统计；整个多轮任务包含分析、工具决策、压缩、修正重试等全部调用。上游 usage 与保守估算分开。 |

未完成完整标签或人工事实复核的指标标为“未评测 / N/A”，不为取得数字改名或填 0/100%。旧报告的自动硬规则通过率保留原名和原始证据，不追认成最终任务成功率。参考 [Ragas Agent 指标](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/agents/) 与 [τ-bench](https://arxiv.org/abs/2406.12045) 的目标达成和重复可靠性定义；项目数据集是自建旅行场景，不能称为跑过这些公开基准。

性能计时从客户端发送请求开始，到首个非空正文 preview/content、完整 completed 和失败终止分别记录。阶段事件、心跳不算正文，首段正文耗时不是首 token 耗时；Android 的打字机动画也不计为模型输出速度。最近秩法取分位数，报告样本量、失败率与范围；A 轨不包括真实高德网络、Nginx、公网和手机渲染。

40 个场景每题重复三次，不是 120 个独立题。正式语义结论需要结合答案和原始工具/数据库/记忆证据复核。新增保留集后才能评估对未见问法的泛化效果。

## 5. 执行控制与结果留存

- 单并发；固定代码提交、题库哈希、模型标识、提供商、采样配置、输入/输出上限、工具超时与总预算。无法固定模型随机种子时如实记录。
- 开始前做健康、鉴权、数据和额度检查。单独执行预热并记录，不混入正式样本；测试顺序使用种子 20261008 打乱，对照版本使用相同次序，避免某类题集中遭遇服务波动。
- 账号在评测批次开始时创建独立临时身份，`alice/bob` 是逻辑引用而非生产账号。重复之间重置偏好、收藏、消息、额度和缓存；预置消息需保留原始角色顺序，不能跳过真正待测的压缩流程。
- 每次消息使用新 `client_message_id`；只有重试同一消息才复用。默认 SSE 作为主轨，JSON 兼容性另测。客户端单调时钟记录 API 链路耗时，不包含手机渲染或打字机动画。
- 保存 manifest、逐步结果、原始回答、结构化需求、工具及候选结果、LLM 调用次数/usage、阶段耗时、请求 ID、人工标签。敏感 Key/Token 不落盘；合成数据与真实评测结果分开，结果默认保留在被 Git 忽略的 `.test-run-agent-evaluation/`。
- 失败不自动换题或从成功率中删除。需要人工裁决的项先标 `needs_review`，全部裁决后才汇总；运行器不能将未知规则默认为通过。

## 6. 对照实验

先完成当前版基线，不直接恢复不兼容旧版生产数据库。参数约束对照优先：在隔离环境使用同一模型、消息、工具快照与预算，对比“规范化+严格校验+一次纠错”和“没有该纠错机制”的链路。缺少可复现的基线实现时只报告当前绝对值，不编造提升幅度。权限和用户隔离在所有实验中保持启用。

记忆实验比较短窗口与当前记忆机制：相同对话、模型、输出预算，比较追问成功率、压缩/回查耗时和累计 Token。SSE 实验保持 Agent 逻辑一致，只比较完整缓冲显示与逐日预览的首段正文等待时间；不能把客户端打字机动画算作模型提速。不同实验单独运行，避免同时改变多个机制。

## 7. 成本与数据验收

先选 H01、R02、W01、D01、P01、M01 各跑一次，测量实际 token 和总耗时；用不同类别成本外推首轮预算。随后跑 40 场景一次，修正运行器/题库问题并冻结版本，最后正式三次重复。先失败再修题后重跑的试运行不能混入正式成绩。

月额度默认 50,000 token 未必够整批，正式运行前根据试跑调整测试账号额度并设置独立批次 token/费用上限；额度不足的正式样本记运行中止和缺测，不冒充模型成功。费用按届时提供商价格计算，本方案不假定固定单价。

题库验收标准：40 个唯一编号、类别数符合约定、每个计分步骤具备必需及禁止条件、所有标准数据引用存在、天气题明确日期轨道、异常题具备注入条件、结果模板与题库步骤一一对应。
