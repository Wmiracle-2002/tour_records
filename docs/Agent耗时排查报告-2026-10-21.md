# Agent耗时排查报告

日期：2026-10-21。结论：当前实测主要瓶颈在模型需求解析和行程生成，不在高德查询或SQLite。先处理模型输出上限、流式终止和阶段预算，再优化模型调用与提示词；工具并行收益较小。

## 1. 测试范围与方法

- 用户授权最多4条规划、累计不超过40,000 Token；实际发送4条用户消息、8次模型HTTP请求，另1次需求解析在发往模型前被本地额度预留拒绝。
- 使用服务器正在运行的原镜像、`deepseek-v4-pro-0813`和真实高德。生产数据不挂载，独立SQLite、随机认证密钥及测试账号，未重启或修改生产服务。
- 单并发，每场景1次，无额外付费预热。首条与后续请求可能受连接预热及供应商波动影响，不以这4条计算稳定P95，也不能据此断言天数或偏好单独造成了某个差值。
- 通过真实回环HTTP调用登录、建会话、发送`/api/v1/agent/chat/stream`。计时从发送消息到SSE终止，不含登录、建会话、预置数据、Nginx、公网及Android渲染。
- 在独立探针进程中给原业务方法加嵌套计时，不修改生产源码。主阶段只统计Agent根节点的直接子阶段；模型、工具等子项用于解释父阶段，不重复相加。
- 最近7天生产日志中没有可用Agent请求，因此本报告全部耗时来自本次补测，不拼接旧评测批次。

## 4. 已定位的问题

### A. 模型生成占主要时间，且两条耗尽输出上限

- L01需求解析11.84秒，模型流式生成35.74秒；生成开始后约33.79秒才收到第一个非空正文delta。客户端到首个模型正文delta约46.18秒，直到48.19秒才有可展示正文。
- L02、L03生成分别66.38、77.00秒，异常类型均为`LLMInvalidResponseError`；探针没有收到非空正文delta，两次生成的结算输出均为**4096 Token**，恰好达到当前上限。
- 因此不能将两次归类为“高德慢”或“HTTP 200即模型成功”。模型耗尽输出预算却未产生可解析行程，是本次最高优先级问题。
- 本次未采集供应商`finish_reason`、推理Token明细或首个网络字节时间。可以确认输出达到上限和没有非空正文，尚不能断定全部Token都用于推理，也不能断定只提高上限就能修复。不得记录或展示隐藏推理正文来排查。

### B. 阶段60秒并非流式调用的严格墙钟上限

配置阶段预算60秒、总预算120秒，但实测生成阶段达到66.38、77.00秒。代码将剩余预算作为HTTPX timeout，并在阶段退出时校验；HTTP读取超时约束与连续收到流数据的总耗时不同。流式迭代本身未逐次检查绝对deadline，异常退出也不能依赖正常路径上的结束检查。

这解释了“配置60秒却继续等”的现象。应在流读取期间检查总deadline、阶段deadline和取消信号，而不是继续增加超时值。

### C. 长会话摘要位于请求关键路径

L04有2次摘要模型调用，分别4.943秒、4.246秒，记忆阶段合计9.199秒，发生在需求解析前。随后申请的需求解析预留为`19,798输入UTF-8字节 + 4,096输出 = 23,894`，而测试账本尚余10,577 Token，因此本地拒绝。

这是**本次测试上限与保守预留规则触发**，不是上游模型账户额度耗尽或网络故障。L04需求解析及规划耗时缺测，不计为0，不追加第五条付费请求绕过限制。

### D. 有攻略并不代表攻略被使用

L03持久化的偏好为`喜欢历史文化`、`参考我收藏的攻略`，代码将其整段作为关键词交集查询。后者是操作意图，前者含表达性前缀；预置笔记无法满足原样交集，实际召回0篇。

已在下载的隔离数据库上只读复现：原关键词返回0篇，仅使用主题`历史文化`返回1篇。应区分检索主题、硬约束与操作意图，不能把所有preferences直接作为必须命中的词。这个问题影响答案质量，不是本次主要耗时来源。

## 5. 优化优先级

|优先级|优化内容|证据与预期范围|
|---|---|---|
|P0|记录流式终止原因、输出用量、正文长度及供应商提供的推理Token计数；对达到上限且无正文单独分类|两条生成各消耗4096输出Token而失败；仅记录元数据，不记录隐藏推理内容|
|P0|验证当前模型的推理模式与结构化输出配置；按阶段选择模型／输出预算，缩减生成任务复杂度|生成35.74～77.00秒；先验证协议和预算，不直接统一提高上限，也不未经评测更换线上模型|
|P0|流式读取执行绝对deadline与取消检查，明确失败及降级原因|避免阶段预算60秒仍等待77秒，降低无效长等待；不保证提高答案成功率|
|P1|精简需求提取的schema与上下文；明确、无歧义的简单输入评估规则提取，复杂输入仍交给LLM|需求解析9.06～14.48秒；当前这3条输入请求均约8KB UTF-8字节。优化后需验证城市、日期、偏好与历史追问不退化|
|P1|评估按天／分块生成与先生成紧凑结构，再由程序补充展示|降低单次输出预算压力并更早产出可校验内容；必须统一跨天去重，不可直接并行独立生成每天；实际收益未测|
|P1|在有输入预算兜底前提下，将合适的摘要处理移到轮次结束或后台，保留原文指针|本次摘要增加约9.2秒；不能为了省时间删除原文或取消输入上限|
|P1|将知识库的主题、硬条件与操作指令分开，修正“参考攻略”被当检索词|离线已复现0篇→1篇；改善知识利用，不宣称显著提速|
|P2|景点、美食HTTP有限并行；主线程归并结果与记录SQLite|按实测两项耗时推算，理想可省**0.234／0.251／0.242秒**，仅占总耗时约**0.49%／0.33%／0.26%**；不是已实现或已测的提速|
|P2|改进Token预估并明确余额与预留不足的提示|UTF-8字节保守估算导致尚余Token却无法预留，需更准确估算；不得放弃硬额度保护|

暂不优化数据库、规则校验、JSON格式化：本次耗时远小于模型调用。尚无依据开展数据库迁移、服务器扩容或全链路异步重写。
